# Selenium Automation Framework

A reusable Selenium and TestNG automation framework built with Java 25 and Maven. It contains Flipkart UI tests alongside reusable API, database, reporting, configuration, and optional AI failure-analysis utilities.

## Overview

This framework is structured to keep the core automation infrastructure reusable across applications while isolating Flipkart-specific page objects and test logic. The primary focus is safe public UI validation against the Flipkart website, plus generic API and database utilities for broader SDET automation patterns.

## Installation

1. Install Java 25.
2. Install Maven.
3. Clone the repository.
4. Run:

```bash
mvn clean test
```

## Running Tests

### Default

```bash
mvn clean test
```

### Headless

```bash
mvn test -Dheadless=true
```

### Browser selection

```bash
mvn test -Dbrowser=chrome
mvn test -Dbrowser=edge
mvn test -Dbrowser=firefox
```

### Parallel execution

The suite uses TestNG parallel mode and a small thread count defined in `src/test/resources/testng.xml`.

## Configuration

Configuration is managed centrally by `ConfigManager` and supports system property overrides, for example:

```bash
mvn test -Dbrowser=chrome -Dheadless=true -DbaseUrl=https://www.flipkart.com
```

Files under `src/test/resources/config` provide default values.

## Reporting

The framework creates HTML reports in `test-output/reports` using ExtentReports. Failed tests attach screenshots automatically when available.

## Screenshots

Screenshots are stored under `test-output/screenshots` using timestamped names. On failures, screenshot paths are attached to the report and logged.

## API Testing

The reusable API layer wraps REST Assured for GET/POST/PUT/PATCH/DELETE calls. Example endpoints use a safe public API (`https://jsonplaceholder.typicode.com`). This keeps the framework generic while remaining non-destructive.

## Database Utility

Database utilities use JDBC and configuration values from properties. If values are absent, database tests are skipped gracefully instead of failing the framework.

## AI-Powered Failure Analysis

When enabled, the existing TestNG listener can send a bounded, redacted failure context to TypeSafe Jev for structured failure triage. The analyzer reports a category, probable cause, confidence, and a recommended debugging action in the Extent report. The provider is isolated behind `AiProvider`; a deterministic mock provider is available for offline development and tests.

The default is disabled:

```properties
ai.enabled=false
ai.provider=jev
ai.timeout.seconds=5
```

Enable TypeSafe Jev by setting its documented `TYPESAFE_API_KEY` environment variable and opting in:

```powershell
$env:TYPESAFE_API_KEY = "your-key"
mvn clean test -Dheadless=true -Dbrowser=chrome -Dai.enabled=true -Dai.provider=jev
```

For local/offline triage testing without credentials or external AI requests:

```powershell
mvn clean test -Dheadless=true -Dbrowser=chrome -Dai.enabled=true -Dai.provider=mock
```

To explicitly disable it on a run:

```powershell
mvn clean test -Dheadless=true -Dbrowser=chrome -Dai.enabled=false
```

The Jev provider uses the documented `POST https://api.typesafe.ai/v1/systemone` endpoint and TypeSafe's `Choice`/`Score` request and response schema. It does not send screenshots, URL query parameters, cookies, browser storage, or credentials. Exception text and stack traces are bounded and common secret-like values are redacted. AI requests have a short timeout; provider failures do not alter the Selenium test result. A malformed AI response is replaced with a low-confidence, evidence-only fallback rather than a fabricated diagnosis.

Example report section:

```text
AI Failure Analysis
Category: ELEMENT_NOT_FOUND
Probable Cause: the target element was not present in the loaded page state
Confidence: HIGH
Recommended Action: Check the locator against the current page DOM and screenshot.
Explanation: Jev selected ELEMENT_NOT_FOUND based on supplied failure evidence.
```

Only enable remote analysis if the test failure context may be sent to TypeSafe. Do not put API keys in properties files or source control; `.env.example` documents the variable name but is not loaded automatically.

## Adding a Page Object

1. Create a new class under `src/test/java/com/sourav/flipkart/pages`.
2. Extend the `BasePage` class.
3. Encapsulate locators and actions in page methods.
4. Keep assertions in the test layer, not in the page object layer.

## Adding a Test

1. Create a test class under `src/test/java/com/sourav/flipkart/tests`.
2. Extend `BaseTest`.
3. Use `@Test(retryAnalyzer = RetryAnalyzer.class)` when appropriate.
4. Use page objects and data providers rather than hardcoded selectors.

## Adding a New Environment

1. Add a new file under `src/test/resources/config` such as `config-staging.properties`.
2. Set the `environment` value or pass `-Denvironment=staging` as a system property.
3. Ensure the relevant base URL and optional API/database configuration are defined.

## CI/CD

A GitHub Actions workflow is included at `.github/workflows/selenium-tests.yml` and runs Maven tests headlessly.

## Known Limitations

- Public websites may introduce anti-bot or login flows; tests should fail gracefully and skip when automation is blocked.
- Some UI selectors may evolve over time; use resilient selectors and explicit waits.
- Live product pages may vary by region and promotional state.

## Flipkart Automation Limitations

- Do not submit orders, payment details, or bypass CAPTCHA.
- Avoid anti-bot workaround attempts.
- Fail gracefully if login prompts, overlays, or bot protections appear.
- Keep automation to safe public browsing and UI validation flows.
